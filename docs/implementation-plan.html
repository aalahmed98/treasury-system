Phase 0

Design and decisions

Done2 November 2026

Understand the bank's existing landscape and decide what to build, for whom, and where the data comes from.

Findings

  • Core banking is TCS BaNCS, live since 2019. Treasury trading and risk is Finastra Fusion Kondor, upgraded in 2020. Transaction banking and liquidity is Infosys Finacle. Retail digital is Backbase. Service management is ServiceNow.
  • Three systems carry a deal at different times: Kondor (front office), Bloomberg (execution), Quantum (back office). Deals appear in one before another and reconciliation breaks.
  • Kondor carries no extra licence cost for our use; Bloomberg and Quantum likely do.

Decisions

  • Do not rebuild the core or Kondor. Consolidate read-only and build the golden record on top.
  • The product is trader decision support for intraday liquidity, not a regulatory book of record. Books of record stay authoritative. Nothing is ever written back to a source.
  • Host on-premises in the bank's data centre, avoiding a Central Bank of Bahrain outsourcing review in the first phase.
  • Working assumption for data access: a read replica with change data capture; vendor export feeds as the fallback.
  • Native Windows desktop application, Rust throughout, Postgres with entitlements enforced in the database.
Phase 1

Foundation

Done3 November 2026

Prove the parts that do not depend on the bank: the data model, desk entitlements, login, and a native client that shows each user only their desks' deals, updated live.

Delivered

  • Postgres 16 with row-level security. Identity is set per transaction; the policies decide what each user reads and books. An unset identity sees nothing.
  • Login with argon2id passwords and hashed session tokens.
  • axum API with server-sent events: a deal booked by one user appears for every entitled user within a second.
  • egui desktop client with a virtualised blotter, positions panel and status bar, built as a Windows executable.
  • Mock desks FX, Money Market, ALM and Treasury Head with five seeded users.

Evidence

  • Integration tests on fresh databases for the entitlement matrix, booking policy, session expiry, token hashing, the login flow and change notification.
  • End-to-end script: four users see different deal counts; a deal inserted directly in Postgres reaches the entitled subscriber only.
Phase 1H

Security hardening

Done3 November 2026

Close everything a review of the foundation found, before anyone other than the developer connects.

Confirmed issues, fixed

  • The application role could grant itself entitlements, create users and read password hashes. Credentials moved behind definer-rights functions; the role holds runtime grants only.
  • The amendment policy let a deal be moved from a read-only desk into a bookable one. Booking rights are now required on the deal's own desk and identity columns are frozen.
  • An open event stream outlived its session. Streams close on logout and re-check the session and entitlements every ten seconds.

Hardening

  • No passwords in migrations; roles created from the environment; owner is not a superuser.
  • Plaintext HTTP only on loopback; TLS supported with a development certificate generator.
  • Per-username lockout after five failures, applied to unknown usernames too; per-IP attempt limit; idle timeout with passive requests that do not count as activity.
  • Fixed, validated server address in the client; optional certificate pinning; passwords redacted from debug output; audit rows carry client address and request id.

Dependency audit: no vulnerabilities; four unmaintained notices in font and Linux clipboard crates.

Phase 2A

Reconciliation core

Done3 November 2026

The product itself: ingest observations from every source, match them into golden deals, track lifecycle per source, enforce expected-lag SLAs, raise breaks, and let the desk resolve them with an audit trail.

Delivered

  • One append-only event log of full images, deduplicated by hash. The golden record is a replayable projection of it; a rebuild reproduces the same deals and links.
  • A separate reconciler process with its own least-privilege database role.
  • Deterministic tiered matching: own reference, cross reference, then economics with strict and relaxed tolerances. Ambiguity and double bookings become breaks, never guesses. Arrival order does not change the outcome.
  • Per-source lifecycle, economics owned by the highest-precedence source, confirmation from the back office, mismatch breaks that resolve themselves when a later image agrees.
  • SLA monitor: missing sources after the expected lag, orphans after a grace window, gated by feed heartbeats so a stale feed does not flood the desk with breaks.
  • Internal bookings as the anchor: a provisional deal created from an external source is folded into the desk's own booking.
  • Synthetic Kondor, Bloomberg and Quantum feeds with lag, drops, duplicates, out-of-order delivery, rounding, counterparty name variants and reversed quotes. Five trading days replay in about forty seconds and produce every break kind.
  • APIs for provenance, breaks, acknowledge, link, dismiss and feed freshness. Client blotter with match status and sources, a sources tab with disagreements highlighted, a breaks tab with actions, and feed ages in the status bar.

Evidence

  • 20 unit tests on calendar, tolerances, normaliser, matcher and SLA maths.
  • 12 pipeline scenarios on fresh databases: three-way match, reversed quote, mismatch then correction, missing then late arrival, orphan then manual link, ambiguity, duplicates, amend before new, cancel propagation, internal anchor, poisoned event, rebuild.
  • 7 privilege-boundary tests and 3 HTTP tests for the new role and endpoints; the 14 foundation tests still pass.
  • End-to-end script from an empty database, including a rebuild that reproduced 200 deals and 554 links exactly.

Known limitation: a user action on a break raised by an SLA tick cannot be replayed by a rebuild, because the break returns with a new id. The rebuild reports how many such actions were skipped.
